Guion de Postman para el viernes

Caso 5 · Red de Apoyo y Salud Mental Universitaria. Cada integrante escribe una petición desde cero en Postman, explica qué hace y muestra un caso de error. El mismo caso pasa de mano en mano: Alfaro crea la solicitud, Briones la clasifica y asigna, Méndez la atiende y la cierra.

  • 1 Fajardo · registro y login
  • 2 Alfaro · crear solicitud
  • 3 Briones · clasificar y asignar
  • 4 Méndez · seguimiento y cierre
  • 5 Mena · talleres y reportes

Antes de empezar

  1. En la carpeta backend: npm run seed y después npm run dev. Debe decir Base de Datos Conectada y Servidor en el puerto 4000.
  2. Abrir http://localhost:4000/api/salud en el navegador. Tiene que responder {"ok":true}.
  3. Abrir Postman con la colección Red de Apoyo · API (Entrega 2) importada. Sirve de respaldo y para mostrar los casos de error.
  4. Tener abierto un bloc de notas para pegar el id de la solicitud que crea Alfaro. Lo usan Briones y Méndez.

Cómo escribir una petición desde cero

Esto es lo que el profe quiere ver. Son los mismos pasos para todos.

  1. Apretar el + de las pestañas de arriba. Se abre una petición vacía.
  2. A la izquierda, elegir el método (GET, POST, PUT, DELETE).
  3. Escribir la URL, por ejemplo http://localhost:4000/api/auth/login.
  4. Si la ruta pide sesión: pestaña Authorization → Auth Type Bearer Token → pegar el token que devolvió el login, sin comillas.
  5. Si se mandan datos: pestaña Body → raw → a la derecha elegir JSON → pegar el JSON.
  6. Send. Abajo se ven el código (200, 201, 400…) y el JSON que respondió el backend.

El token sale en la respuesta del login, en el campo "token". Se copia todo el texto largo que empieza con eyJ, sin las comillas. Dura 20 minutos.

1 · Fajardo

RF1 · Autenticación y estructura del backend

Qué dice

"El backend está hecho en Node con Express y guarda en MongoDB con Mongoose. Cada petición pasa por middlewares: primero se revisa el token, después el perfil, y recién ahí llega al controlador. Voy a registrar un usuario y hacer login para obtener el token que usan todas las demás peticiones."

Petición en vivo 1 · Registrar un usuario

POSThttp://localhost:4000/api/auth/registro
Authorization
No lleva (es pública)
{
  "nombre": "Ana Perez",
  "email": "ana.perez@universidad.cl",
  "password": "clave1234",
  "perfil": "estudiante",
  "unidad": "Ingenieria Civil"
}

201 "Cuenta creada correctamente"

Petición en vivo 2 · Login

POSThttp://localhost:4000/api/auth/login
{
  "email": "ana.perez@universidad.cl",
  "password": "clave1234"
}

200 "Sesion iniciada" + token + datos del usuario (sin la contraseña)

Casos de error para mostrar (desde la colección, carpeta 1)

Login con clave incorrecta → 401 · Perfil sin token → 401 · Registro con datos inválidos → 400

Si el profe pregunta

¿Cómo se guarda la contraseña?Cifrada con bcrypt en un pre("save") del modelo. En Compass se ve como $2b$10$…, nunca la clave real.

¿Y si alguien se registra como admin?Queda con activo: false y el login responde 403 hasta que el admin lo valide. Solo los estudiantes entran de inmediato.

¿Qué es el token?Un JWT firmado con el id y el perfil. Dura 20 minutos (RNF3) y se manda en el header Authorization: Bearer.

2 · Alfaro

RF2, RF3 · Solicitud del estudiante y derivación docente

Qué dice

"Ahora entro como estudiante y pido apoyo. El backend valida los datos, guarda la solicitud y le genera un folio automático. También muestro cómo un docente deriva a un estudiante que ya tiene cuenta."

Petición en vivo 1 · Login del estudiante

POSThttp://localhost:4000/api/auth/login
{
  "email": "estudiante@universidad.cl",
  "password": "clave1234"
}

200 → copiar el token

Petición en vivo 2 · Crear la solicitud

POSThttp://localhost:4000/api/solicitudes
Authorization
Bearer Token → token del estudiante
{
  "motivo": "Academico",
  "descripcion": "Me cuesta concentrarme y estoy durmiendo poco antes de las pruebas.",
  "urgenciaPercibida": "alta",
  "contacto": "Correo institucional"
}

201 "Solicitud creada correctamente" con folio RA-2026-0003 (si se corrió el seed antes) y estado recibida

Importante: copiar el "_id" de la solicitud de la respuesta (no el folio) y dejarlo en el bloc de notas para Briones y Méndez.

Casos de error para mostrar (carpeta 2)

Descripción corta → 400 · Derivar a un correo que no existe → 404

Si el profe pregunta

¿Dónde se genera el folio?En un pre("save") del modelo Solicitud. Cuenta las solicitudes del año y arma RA-año-número; así ningún controlador se olvida de ponerlo.

¿El docente crea cuentas?No. Deriva a un estudiante que ya está registrado, usando su correo. Si no existe, responde 404.

"La solicitud que creó Alfaro llega a la bandeja del orientador. Yo entro como orientador, la clasifico por tipo y le asigno un profesional. Solo el orientador o el admin pueden hacerlo: si lo intenta un estudiante, el backend responde 403."

Casos de error para mostrar (carpeta 3)

Estudiante intenta clasificar → 403 · Asignar sin clasificar → 400

Si el profe pregunta

¿De dónde sale el id en la URL?Es req.params.id. Lo que va en el Body (tipo, profesionalId) llega en req.body.

¿Quién decide el 403?El middleware permitir("orientador", "admin"), antes de llegar al controlador.
